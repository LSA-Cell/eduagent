## 1. 判断口径与项目边界

本文以**当前代码、现有自动化测试和本次实际执行结果**判断现状。设计文档描述目标与约束，不能单独证明功能已经上线。下文的“已落地”表示仓库存在实现，测试与真实环境的验收状态另行标明。它不等于真实设备、真实模型、真实支付或生产部署已经验收。“未通过”“环境阻塞”“尚未验收”分别记录。

本轮输入为第四节的问题清单、现有代码和可见红线；输出为必要的本地修复、回归测试与本文各节更新。用户明确没有现成测试环境，授权范围为“先完成本地修复和全部可执行测试”。保持 Flutter/Dart、FastAPI/Python、PostgreSQL/pgvector、Redis、MinIO、Celery、Compose/Nginx 技术栈和现有目录、接口字段；不增加页面、支付渠道、审核后台、推送平台、模型服务或新依赖。数据库只补齐十张表现有 ORM 已使用的 52 个缺列，不引入新业务字段或表，保留旧列、数据、索引、RLS 和授权。媒体路由落实已有 API 文档第 3 节的入口，不放宽知识库类型、不新增 SSE 事件。本轮未实施第 5、6 节的备选需求。

项目主链路为 Flutter → Nginx/BFF → Agent/Gateway/Multimodal/Proxy/Billing/Docgen → PostgreSQL、Redis、MinIO、vLLM。服务职责和网络拓扑以[架构文档](architecture.md#L7)及当前 [`docker-compose.yml`](../../docker-compose.yml)为准。

模块依赖保持移动端→BFF；BFF 鉴权并转发；Agent 编排并经 Gateway 推理；Multimodal 负责识别；Docgen 负责排版；Billing/Proxy 负责支付状态和额度闸门。原始文件留私有存储，业务记录和用户归属留数据库，长任务留 Celery；配置继续由既有 Settings 与本机环境变量提供。后端按各服务 requirements 安装，Compose 构建/运行；移动端按既有 pubspec 构建，具体验证命令见第 4 节。旧数据库通过独立兼容 SQL 修复，首次初始化包含相同补丁，操作方式见 [README](项目说明.md)。未改网络隔离或暴露端口。

MinIO 专项修复仅调整 Compose 中服务端与建桶工具的镜像构建入口，新增 [`infra/minio/Dockerfile`](../../infra/minio/Dockerfile)：从固定上游提交及 SHA256 校验的源码构建既有 MinIO/mc，保留私有桶初始化、卷、凭证及网络隔离规则。本项修复未修改业务代码、API、数据库或红线设计文件；构建所需 Go 工具仅存在于构建阶段，不进入运行镜像。
